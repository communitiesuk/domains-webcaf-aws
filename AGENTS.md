# Repository Guide

## Runtime and layout

- Use Python 3.14 and uv 0.12.23; `.python-version`, `uv.lock`, and the container images are pinned accordingly.
- `manage.py` is at the repository root. Django configuration and entrypoints are in `webcaf/`; the main application package is `webcaf/webcaf/`.
- Edit templates and static sources under `webcaf/webcaf/templates/` and `webcaf/webcaf/static/`. `webcaf/static/` is the collected-static output, not the source tree.
- CAF definitions live in `frameworks/*.yaml`; `Assessment.get_router()` selects the implementation from `webcaf/webcaf/frameworks.py`.
- Unit/integration tests are in `tests/`. Playwright/Behave scenarios and steps are in `features/`.

## Setup and local services

- For host-based development, copy `webcaf/.env.example` to `webcaf/.env`, run `uv sync`, and run `make up_one_login_simulator` before migrations or tests.
- Host processes and Docker Compose use the One Login simulator by default. DEX is available only through explicit DEX commands; PostgreSQL is exposed on host port 54321.
- `docker compose up` starts the app at `http://localhost:8010`. The one-shot `init` service runs `makemigrations`, `collectstatic`, then `migrate`. Because the repository is bind-mounted, startup can create migration files in the worktree; inspect them rather than assuming startup is read-only.
- `make up-devserver` runs Django's development server in Compose. `make shell` requires the `web` service already running. Use `docker compose down --volumes` only when intentionally deleting local data; the legacy `make clear-db` target is checkout-name-dependent and also prunes unrelated stopped containers.

## Verification

- Run the containerized pytest suite with `make test`; it writes `reports/pytest-report.html` and tears down Compose after a successful run. If pytest fails, run `docker compose down` to clean up supporting services.
- Run a focused host test with `uv run pytest tests/<file>.py::<test>` after PostgreSQL and `webcaf/.env` are available.
- Run the default One Login BDD suite with `make behave`, a single feature with `make behave FEATURE_TEST_ARGS="-i <feature-file>"`, or focused DEX coverage with `make behave_dex`.
- Behave runs in the isolated `webcaf-behave` Compose project with disposable database and cache volumes. The target applies migrations and always removes test resources; `make behave-clean` removes stale test resources explicitly.
- The identifiers in `behave.ini` are cleanup filters used between scenarios, not restrictions on which records scenarios may create. Failures write screenshots, HTML and Compose logs to `artifacts/`.
- The containerized `make behave` flow is headless. Do not run Behave directly against the normal development stack because that bypasses the disposable test database.
- Match PR CI by running `uv run pre-commit run --all` before tests. CI then runs `collectstatic`, migrations, the Django suite, the One Login protocol smoke test, the default One Login BDD suite, and focused DEX BDD coverage.
- For every CAF YAML change, run `uv run pre-commit run check-yaml --files frameworks/<changed-file>.yaml`. For CAF 3.2, also run `uv run python -m unittest tests.test_yaml`; that structural test currently hard-codes CAF 3.2 and does not validate CAF 4.0.

## Repository-specific constraints

- Ruff handles formatting, linting, and import ordering with a 120-character line limit. Use `make lint` for check-only validation and `make format` to apply fixes through the pinned pre-commit hooks.
- Never log raw email addresses or other user identifiers. Import and apply `mask_email` from `webcaf.webcaf.utils` in log messages.
- Database-backed default configuration requires `current_assessment_period`, `assessment_period_end`, and `default_framework`; seeded values are created by migrations.
- Schema migrations belong in `webcaf/webcaf/migrations/`. Do not treat changes generated by Compose startup as disposable without reviewing whether model changes require them.

## Branch naming

- Prefix new work with `feature/`, bug fixes with `bugfix/`, production-critical fixes with `hotfix/`, release preparation with `release/`, and documentation changes with `docs/`.
- Include the project ticket when one exists: `<prefix>/<ticket>-<description>`, for example `feature/T-456-user-authentication` or `docs/T-654-update-readme`.
- Release branches use the release version, for example `release/v2.0.1`.

## Commits

- Every commit message must start with the project ticket number, for example `T-456 Add user authentication`.
- If the user has not supplied a ticket number, ask for it before creating a commit.
